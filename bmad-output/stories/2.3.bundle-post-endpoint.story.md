**Story ID:** 2.3

## Story

**As a** frontend developer
**I want** a REST endpoint to post a constructed bundle to the FHIR server and extract assigned resource IDs
**so that** the results panel can display Patient ID and Observation IDs without handling FHIR server communication or response parsing

1. Given a bundle has been constructed and stored in session state, when POST /api/bundles/post is called with session_id and identifier, then the bundle is posted to the FHIR server and the server response (including assigned FHIR IDs) is returned in the API response [Source: prd.md#FR-008, prd.md#FR-012]

2. Given the FHIR server returns 200 or 201 status, when the response is parsed, then the Patient FHIR ID (if a Transaction Bundle) and all Observation FHIR IDs are extracted from the Bundle response and returned in the data object as patient_id and observation_ids [Source: prd.md#FR-009]

3. Given a Transaction Bundle is posted successfully, when the Patient FHIR ID is extracted, then it is stored in the patient service (via patient_service.set_fhir_id()) so subsequent operations can use Batch Bundles [Source: prd.md#FR-008]

4. Given no bundle exists in session state for the patient, when POST /api/bundles/post is called, then a 400 response is returned with error code NO_BUNDLE [Source: architecture.md#ADR-005]

5. Given an unknown patient identifier, when POST /api/bundles/post is called, then a 400 response is returned with error code PATIENT_NOT_FOUND [Source: architecture.md#ADR-005]

6. Given the FHIR server is unreachable, when the bundle is posted, then a 502 response is returned with error code FHIR_SERVER_UNREACHABLE [Source: architecture.md#ADR-005]

7. Given the FHIR server returns an error (4xx or 5xx), when the response is received, then a 502 response is returned with error code FHIR_SERVER_ERROR and the server's error message is included in the details field [Source: architecture.md#ADR-005]

### Architecture Pattern

This story implements the POST /api/bundles/post endpoint in the FastAPI backend following the REST pattern from ADR-001. It extends the bundles router and bundle_service created in Story 2.2. The endpoint posts the constructed bundle to the local InterSystems FHIR server, parses the response, and extracts assigned FHIR IDs. [Source: architecture.md#ADR-001, architecture.md#4-component-design]

The bundle_service.py layer is responsible for:
- Retrieving the constructed bundle from session state (stored by Story 2.2)
- Posting the bundle to the FHIR server with Basic auth credentials (from env vars per ADR-003)
- Parsing the FHIR server's Bundle response to extract assigned FHIR IDs
- Storing the Patient FHIR ID (if Transaction Bundle) in the patient service for future Batch Bundle operations
- Handling FHIR server errors and connection failures

### Data Model

After posting, the Patient FHIR ID is stored in the patient service's in-memory patient data structure (managed by patient_service.py, created in Story 1.2). The FHIR ID is keyed by patient identifier.

```python
# In patient_service (simplified):
patients[identifier].fhir_id = extracted_patient_id
```

The extracted IDs (patient_id, observation_ids) are returned in the API response but not stored long-term in session state. [Inference: IDs are displayed in the UI, but rebuilding the bundle and posting again would generate new IDs]

[Source: architecture.md#ADR-004, architecture.md#5-data-model]

### Integration Points

- **Session state (bundle):** The bundle service retrieves the constructed bundle stored by Story 2.2 from session state, keyed by session_id and patient identifier. If no bundle exists, return NO_BUNDLE error. [Source: architecture.md#ADR-004]

- **Patient service dependency:** After successfully posting a Transaction Bundle, the bundle service must call patient_service.set_fhir_id(identifier, fhir_id) to store the Patient's FHIR ID. This enables future Batch Bundle operations (the next time the user generates observations and builds a bundle for this patient, Story 2.2's auto-selection logic will choose Batch instead of Transaction). [Source: prd.md#FR-008, architecture.md#4-component-design]

- **FHIR server:** The bundle service posts the bundle JSON to the FHIR server using the `requests` library. The FHIR server URL and credentials are read from environment variables (config.py, established in Story 1.1). [Source: architecture.md#ADR-003]
  - URL: `FHIR_SERVER_URL` (default: `http://127.0.0.1:8080/csp/healthshare/demo/fhir/r4`)
  - Auth: Basic auth with `FHIR_SERVER_USER` and `FHIR_SERVER_PASS` (defaults: `_System`, `ISCDEMO`)
  - Endpoint: POST to `{FHIR_SERVER_URL}` (the base URL accepts Bundle posts)
  - Headers: `Content-Type: application/fhir+json`

- **FHIR server response format:** The FHIR server returns a Bundle of type `transaction-response` or `batch-response`. Each entry in the response has a `response` object with:
  - `status` (e.g., "201 Created")
  - `location` (e.g., "Patient/742/_history/1" or "Observation/743/_history/1")

  The FHIR ID is extracted from the `location` field. Parse the location string to extract the ID (e.g., "Patient/742/_history/1" → ID is "742").

  [Inference: use regex or string split to extract ID from location. Format is `{ResourceType}/{ID}/_history/{version}`]

### FHIR ID Extraction Logic

The FHIR server's response Bundle contains an entry for each resource posted. Each entry has a `response.location` field with the assigned FHIR ID.

```python
# Pseudocode for ID extraction
server_response_bundle = response.json()  # FHIR Bundle response
patient_id = None
observation_ids = []

for entry in server_response_bundle["entry"]:
    location = entry.get("response", {}).get("location", "")
    # Location format: "Patient/742/_history/1" or "Observation/743/_history/1"
    if "Patient/" in location:
        patient_id = extract_id_from_location(location)  # Extract "742"
    elif "Observation/" in location:
        obs_id = extract_id_from_location(location)  # Extract "743"
        observation_ids.append(obs_id)

def extract_id_from_location(location: str) -> str:
    # Parse "Patient/742/_history/1" → return "742"
    parts = location.split("/")
    if len(parts) >= 2:
        return parts[1]
    return ""
```

If the bundle is a Transaction Bundle, `patient_id` will be extracted and stored via `patient_service.set_fhir_id(identifier, patient_id)`. If the bundle is a Batch Bundle, `patient_id` will be None (only observations are posted).

### Error Handling

All errors must be returned in the standardized response envelope [Source: architecture.md#ADR-005]:
- NO_BUNDLE (400): No bundle exists in session state for the patient — instruct user to build a bundle first
- PATIENT_NOT_FOUND (400): Patient identifier not found in loaded patients
- FHIR_SERVER_UNREACHABLE (502): Connection to FHIR server failed (connection refused, timeout, network error)
- FHIR_SERVER_ERROR (502): FHIR server returned an error status (4xx, 5xx) — include the server's error message in details
- INTERNAL_ERROR (500): Unexpected exceptions during posting or response parsing

### Notes for Implementation

- **Pydantic v1:** The backend uses Pydantic v1 (pinned by fhir.resources 6.1.0). Use `.dict()` and `.json()` methods, not v2 syntax. [Source: architecture.md#trade-off-pydantic-v1-compatibility]

- **Bundle JSON serialization:** The bundle stored in session state (from Story 2.2) is already a dict. Convert to JSON string for posting to the FHIR server. Use `json.dumps(bundle_json)` or `requests.post(..., json=bundle_json)` which handles serialization automatically.

- **FHIR server response parsing:** The server response is a FHIR Bundle with type `transaction-response` or `batch-response`. Parse the JSON response and extract the `entry` array to iterate through response locations.

- **Patient FHIR ID storage:** After extracting the Patient FHIR ID from a Transaction Bundle response, call `patient_service.set_fhir_id(identifier, patient_id)`. This updates the in-memory patient data so future calls to Story 2.2 (bundle build) will select Batch Bundle instead of Transaction Bundle for this patient. [Source: prd.md#FR-008]

- **Entry count validation:** [Inference] Optionally validate that the number of entries in the server response matches the number of entries in the posted bundle. If counts don't match, log a warning or include in the message (e.g., "Bundle posted — expected 101 entries, received 101 responses").

- **Server response inclusion:** Return the full server response Bundle in the API response (`server_response` field) so the frontend can display raw FHIR JSON if needed for debugging or demonstration purposes. [Inference: helpful for teaching tool to show full server response]

**Integration tests** for routers/bundles.py:
- Test POST /api/bundles/post with valid session_id, identifier, and existing Transaction Bundle — verify 200 response with patient_id, observation_ids, bundle_type="transaction", and server_response
- Test POST /api/bundles/post with valid session_id, identifier, and existing Batch Bundle — verify 200 response with patient_id=null, observation_ids, bundle_type="batch", and server_response
- Test POST /api/bundles/post with no bundle in session — verify 400 response with NO_BUNDLE error code

**Edge cases:**

- FHIR server returns 201 for some entries and 4xx for others (partial success) — verify error handling (treat as FHIR_SERVER_ERROR with details)
