## Story

**As a** frontend developer
**I want** a REST endpoint to build a FHIR Bundle with automatic selection of Batch vs Transaction type
**so that** the bundle panel can display the constructed bundle JSON and bundle type indicator without implementing FHIR bundle logic

1. Given observations exist in session state for a patient with no known FHIR server ID, when POST /api/bundles/build is called with session_id and identifier, then a Transaction Bundle is constructed containing the Patient resource (with urn:uuid fullUrl) and all observations (with subject references to the Patient urn:uuid), and the response includes bundle_type="transaction", bundle_type_reason, entry_count, and full bundle_json [Source: prd.md#FR-005, prd.md#FR-007]

2. Given observations exist in session state for a patient with a known FHIR server ID, when POST /api/bundles/build is called, then a Batch Bundle is constructed containing only the observations (with subject references to the Patient FHIR ID), and the response includes bundle_type="batch", bundle_type_reason, entry_count, and full bundle_json [Source: prd.md#FR-006, prd.md#FR-007]

3. Given no observations exist in session state for the patient, when POST /api/bundles/build is called, then a 400 response is returned with error code NO_OBSERVATIONS [Source: architecture.md#ADR-005]

4. Given an unknown patient identifier, when POST /api/bundles/build is called, then a 400 response is returned with error code PATIENT_NOT_FOUND [Source: architecture.md#ADR-005]

5. Given a bundle is constructed, when it is stored in session state, then it is keyed by session_id and patient identifier so POST /api/bundles/post (Story 2.3) can retrieve it [Source: architecture.md#ADR-004]

6. Given a Transaction Bundle is constructed, when the bundle JSON is returned, then each entry shows request.method="POST" and request.url matches the resource type (e.g., "Patient", "Observation"), and the Patient entry uses a urn:uuid fullUrl that observations reference in their subject field [Source: prd.md#FR-005]

7. Given a Batch Bundle is constructed, when the bundle JSON is returned, then each entry shows request.method="POST" and request.url="Observation", and all observations reference the patient's known FHIR ID in their subject field [Source: prd.md#FR-006]

### Architecture Pattern

This story implements the POST /api/bundles/build endpoint in the FastAPI backend following the REST pattern from ADR-001. It wraps the existing BatchBundle and TransactionBundle classes from batchbundle.py and transactionbundle.py. [Source: architecture.md#ADR-001, architecture.md#4-component-design]

The bundle_service.py layer is responsible for:
- Retrieving observations from session state (stored by Story 2.1)
- Querying patient_service to determine if the patient has a known FHIR server ID
- Selecting the appropriate bundle type (Batch or Transaction) based on FHIR ID presence
- Constructing the bundle using existing Python classes
- Storing the constructed bundle in session state for retrieval by Story 2.3 (bundle post endpoint)

### Data Model

Bundles are stored in session state keyed by `session_id` and `patient identifier`. The session state schema (from state.py, established in Story 1.1 and extended in Story 2.1) includes:
```python
bundles: dict[str, dict[str, dict]]
# Outer key: session_id (UUID)
# Inner key: patient identifier (e.g., "356-444-9972")
# Value: dict with bundle_type ("batch" or "transaction"), bundle_json (full Bundle resource), and entry_count
```
[Source: architecture.md#ADR-004, architecture.md#5-data-model]

### Functional Requirements

**FR-005:** Transaction Bundle construction [Source: prd.md#FR-005]
- If patient has no known FHIR server ID, construct a Transaction Bundle
- Bundle contains Patient entry with urn:uuid fullUrl and Observation entries with subject references to that UUID
- Each entry has request.method="POST" and request.url matching the resource type

**FR-006:** Batch Bundle construction [Source: prd.md#FR-006]
- If patient has a known FHIR server ID, construct a Batch Bundle
- Bundle contains only Observation entries (patient is already on server)
- Each observation's subject references the patient's FHIR ID directly
- Each entry has request.method="POST" and request.url="Observation"

**FR-007:** Bundle type auto-selection [Source: prd.md#FR-007]
- System automatically selects Transaction or Batch based on patient FHIR ID presence
- Response includes bundle_type ("transaction" or "batch") and bundle_type_reason explaining the choice
- Frontend displays this indicator so learners understand the selection logic

**FR-012:** Backend API for bundle operations [Source: prd.md#FR-012]
- POST /api/bundles/build constructs the appropriate bundle type and returns bundle JSON
- Constructed bundle is stored in session state for later posting

### API Contract

**POST /api/bundles/build**
Request body:
```json
{
  "session_id": "uuid-string",
  "identifier": "356-444-9972"
}
```

Success response (200) — Transaction Bundle:
```json
{
  "success": true,
  "data": {
    "bundle_type": "transaction",
    "bundle_type_reason": "Patient has no FHIR server ID — using Transaction Bundle with urn:uuid references",
    "entry_count": 101,
    "bundle_json": {
      "resourceType": "Bundle",
      "type": "transaction",
      "entry": [
        {
          "fullUrl": "urn:uuid:12345678-...",
          "resource": { "resourceType": "Patient", ... },
          "request": { "method": "POST", "url": "Patient" }
        },
        {
          "resource": { "resourceType": "Observation", "subject": { "reference": "urn:uuid:12345678-..." }, ... },
          "request": { "method": "POST", "url": "Observation" }
        },
        ...
      ]
    }
  },
  "message": "Transaction Bundle built with 101 entries"
}
```

Success response (200) — Batch Bundle:
```json
{
  "success": true,
  "data": {
    "bundle_type": "batch",
    "bundle_type_reason": "Patient has known FHIR server ID — using Batch Bundle with direct references",
    "entry_count": 100,
    "bundle_json": {
      "resourceType": "Bundle",
      "type": "batch",
      "entry": [
        {
          "resource": { "resourceType": "Observation", "subject": { "reference": "Patient/742" }, ... },
          "request": { "method": "POST", "url": "Observation" }
        },
        ...
      ]
    }
  },
  "message": "Batch Bundle built with 100 entries"
}
```

Error response (400 NO_OBSERVATIONS):
```json
{
  "success": false,
  "error": {
    "code": "NO_OBSERVATIONS",
    "message": "No observations found for patient 356-444-9972",
    "details": "Generate observations before building a bundle"
  }
}
```

Error response (400 PATIENT_NOT_FOUND):
```json
{
  "success": false,
  "error": {
    "code": "PATIENT_NOT_FOUND",
    "message": "Patient with identifier 356-444-9972 not found",
    "details": ""
  }
}
```
[Source: architecture.md#ADR-005, architecture.md#6-api-specifications]

### Integration Points

- **Existing Python classes:** The service layer must instantiate and call existing classes (BatchBundle, TransactionBundle from batchbundle.py and transactionbundle.py). These classes may use `print()` for output — the service layer must capture return values (bundle JSON) instead. [Inference: refactor may be required to replace prints with returns]

- **Session state (observations):** The bundle service retrieves observations generated in Story 2.1 from session state, keyed by session_id and patient identifier. If no observations exist, return NO_OBSERVATIONS error. [Source: architecture.md#ADR-004]

- **Patient service dependency:** The bundle service must query patient_service (services/patient_service.py, created in Story 1.2) to:
  1. Validate the patient identifier exists (return PATIENT_NOT_FOUND if not)
  2. Retrieve the patient's FHIR server ID (fhir_id field) to determine bundle type
  3. Get the full Patient resource for inclusion in Transaction Bundles
  [Source: architecture.md#4-component-design]

- **urn:uuid generation:** For Transaction Bundles, generate a UUID for the Patient resource fullUrl (e.g., urn:uuid:12345678-1234-1234-1234-123456789abc). All observations in the bundle must reference this UUID in their subject.reference field. [Inference: use Python's uuid.uuid4() for generation]

### Bundle Type Auto-Selection Logic

The selection logic is central to FR-007:

```python
# Pseudocode
patient = patient_service.get_patient(identifier)
if patient is None:
    raise PatientNotFoundError

if patient.fhir_id is None or patient.fhir_id == "":
    # No FHIR ID → Transaction Bundle
    bundle_type = "transaction"
    bundle_type_reason = "Patient has no FHIR server ID — using Transaction Bundle with urn:uuid references"
    bundle = build_transaction_bundle(patient, observations)
else:
    # FHIR ID exists → Batch Bundle
    bundle_type = "batch"
    bundle_type_reason = "Patient has known FHIR server ID — using Batch Bundle with direct references"
    bundle = build_batch_bundle(patient.fhir_id, observations)
```
[Source: prd.md#FR-007]

### Naming Conventions

- **Backend:** snake_case for all Python variables, functions, file names. PascalCase for class names. [Source: architecture.md#ADR-006]
- **Router file:** routers/bundles.py
- **Service file:** services/bundle_service.py
- **Request model:** models/requests.py (BundleBuildRequest)
- **Response model:** models/responses.py (BundleBuildResponse, extend ApiResponse if needed)
- **Endpoint path:** /api/bundles/build (lowercase, kebab-case)
- **JSON keys:** snake_case (session_id, identifier, bundle_type, bundle_type_reason, entry_count, bundle_json)

### Error Handling

All errors must be returned in the standardized response envelope [Source: architecture.md#ADR-005]:
- NO_OBSERVATIONS (400): No observations exist in session state for the patient — instruct user to generate observations first
- PATIENT_NOT_FOUND (400): Patient identifier not found in loaded patients
- INTERNAL_ERROR (500): Unexpected exceptions during bundle construction

### Notes for Implementation

- **Pydantic v1:** The backend uses Pydantic v1 (pinned by fhir.resources 6.1.0). Use `.dict()` and `.json()` methods, not v2 syntax. [Source: architecture.md#trade-off-pydantic-v1-compatibility]

- **Bundle JSON serialization:** The existing BatchBundle and TransactionBundle classes return Bundle instances (fhir.resources.Bundle). Convert to dict using `.dict()` before storing in session state and returning in API response. [Inference: ensure FHIR resource serialization is correct]

- **Entry count:** Return the total number of entries in the bundle (entry_count). For Transaction Bundles, this is 1 (Patient) + N (Observations). For Batch Bundles, this is N (Observations only).

- **Session state storage:** Store the constructed bundle in session state so Story 2.3 (bundle post endpoint) can retrieve it without rebuilding. Store both the bundle JSON (dict) and metadata (bundle_type, entry_count). [Inference: if user rebuilds bundle, overwrite previous bundle]

- **Transaction Bundle urn:uuid:** The urn:uuid for the Patient must be consistent within the bundle — generated once and used in both the Patient entry's fullUrl and all Observation entries' subject.reference. [Inference: generate UUID at start of build_transaction_bundle()]

- **Batch Bundle patient reference:** Observations reference the patient using "Patient/{fhir_id}" format (e.g., "Patient/742"). [Source: prd.md#FR-006]

### Testing Strategy

**Unit tests** for services/bundle_service.py:
- Test build_bundle() with patient that has no FHIR ID and valid observations — verify Transaction Bundle constructed, bundle_type="transaction", bundle_type_reason correct, entry_count = 1 + N observations
- Test build_bundle() with patient that has a known FHIR ID and valid observations — verify Batch Bundle constructed, bundle_type="batch", bundle_type_reason correct, entry_count = N observations
- Test build_bundle() with no observations in session state — verify NO_OBSERVATIONS error raised
- Test build_bundle() with unknown patient identifier — verify PATIENT_NOT_FOUND error raised
- Test build_transaction_bundle() — verify urn:uuid generated, Patient entry included, all observations reference the UUID in subject.reference
- Test build_batch_bundle() — verify no Patient entry, all observations reference known FHIR ID in subject.reference
- Test that constructed bundle is stored in session state keyed by session_id and identifier

**Integration tests** for routers/bundles.py:
- Test POST /api/bundles/build with valid session_id, identifier, and existing observations (no FHIR ID) — verify 200 response with bundle_type="transaction", bundle_json contains Patient + Observations with urn:uuid references
- Test POST /api/bundles/build with valid session_id, identifier, and existing observations (with FHIR ID) — verify 200 response with bundle_type="batch", bundle_json contains only Observations with Patient/{id} references
- Test POST /api/bundles/build with no observations in session — verify 400 response with NO_OBSERVATIONS error code
- Test POST /api/bundles/build with unknown patient identifier — verify 400 response with PATIENT_NOT_FOUND error code
- Test that bundle JSON structure matches FHIR Bundle spec (resourceType="Bundle", type="transaction" or "batch", entry array with fullUrl/resource/request)

**Edge cases:**
- Empty or malformed request body — verify 422 Unprocessable Entity (FastAPI default validation)
- Missing session_id in request — verify validation error
- Observations exist but are empty list — verify NO_OBSERVATIONS error
- Patient FHIR ID is empty string ("") vs None — verify Transaction Bundle is chosen (treat empty string as no ID)

**Fixtures and mocks:**
- Mock session state (state.py) for unit tests with pre-populated observations
- Mock patient service (services/patient_service.py) to simulate patients with and without FHIR IDs
- Mock or stub existing batchbundle.py and transactionbundle.py classes if needed to isolate service layer logic
- Use a test patient with known FHIR ID (e.g., "742") and a test patient with no FHIR ID for integration tests

**Coverage targets:**
- All AC (#1-#7) must have at least one test case proving the criterion
- All error codes (NO_OBSERVATIONS, PATIENT_NOT_FOUND) must be triggered and verified
- Both bundle types (Transaction and Batch) must be covered in integration tests
- Bundle JSON structure must be validated (entry count, fullUrl for Transaction, references for both types)
