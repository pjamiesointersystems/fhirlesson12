# 4.2: Patient Detail Component

**Story ID:** 4.2
**Epic:** 4 — Patient Management UI
**Slug:** patient-detail
**Status:** ready-for-dev

---

## Story

**As an** instructor
**I want** to view the full FHIR Patient JSON resource and post it to the FHIR server
**So that** I can demonstrate patient resource structure and individual resource submission to learners

---

## Acceptance Criteria — LOCKED

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. **Display full FHIR Patient JSON:** Given a patient is selected from the patient list, when the patient detail panel renders, then the complete FHIR Patient resource is displayed as formatted JSON with syntax highlighting.

2. **Required FHIR fields visible:** Given the Patient JSON is displayed, when the instructor reviews the content, then the JSON includes name, address, birthDate, gender, telecom, and identifier fields [Source: prd.md#FR-002].

3. **Placeholder when no selection:** Given no patient is selected (initial app load or selection cleared), when the patient detail panel renders, then a placeholder message "Select a patient to view details" is displayed instead of JSON.

4. **Post Patient button:** Given a patient is selected, when the patient detail panel renders, then a "Post Patient" button is visible below the JSON display.

5. **Post Patient success:** Given a patient is selected and the "Post Patient" button is clicked, when the FHIR server returns success, then the assigned FHIR ID is displayed in the panel and a success message "Patient posted successfully" is shown.

6. **Post Patient error handling:** Given a patient is selected and the "Post Patient" button is clicked, when the FHIR server returns an error or is unreachable, then an error message (from the response envelope) is displayed in the panel.

7. **FHIR ID persistence indicator:** Given a patient has been posted successfully, when the patient detail panel displays that patient again, then the FHIR ID is shown alongside the JSON (e.g., "FHIR ID: 742") to indicate the patient already exists on the server.

## Dev Notes — LOCKED

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

**Architecture:**

This component is part of Epic 4 (Patient Management UI) and implements FR-002 (Patient detail view) and FR-015 (Post patient to FHIR server) [Source: prd.md#FR-002, prd.md#FR-015]. It lives in `frontend/src/app/components/patient-detail/` per ADR-006 naming conventions [Source: architecture.md#ADR-006].

**Data source:**

The component receives a patient identifier from PatientListComponent (story 4.1) — either via @Input, @Output EventEmitter, or a shared service [Inference]. When the identifier changes, the component calls `ApiService.getPatient(identifier)` which hits `GET /api/patients/{identifier}` [Source: architecture.md#6-api-specifications].

Expected response:

```json
{
  "success": true,
  "data": {
    "patient": { "resourceType": "Patient", "name": [...], "identifier": [...], ... },
    "fhir_id": "123" | null
  }
}
```

[Source: architecture.md#6-api-specifications]

The `patient` field contains the full FHIR Patient resource JSON. The `fhir_id` field is null if the patient has not been posted to the FHIR server, or a string ID if it has been posted [Source: architecture.md#5-data-model, Entity: Patient].

**Required FHIR fields (FR-002 AC):**

The PRD states the JSON "includes name, address, birthDate, gender, telecom, and identifier fields" [Source: prd.md#FR-002]. The existing `patients.txt` and `patients.py` classes (being wrapped by the backend) define these fields [Source: sharding-context.md#Existing Python Code Being Wrapped]. The component must display the raw FHIR JSON; it does not need to parse or validate these fields — the JsonViewerComponent will render them as-is [Inference].

**JSON display:**

Use the JsonViewerComponent created in story 3.3 [Source: epics.md#Epic 3, story 3.3]. This component provides syntax highlighting per FR-014 [Source: prd.md#FR-014]. Pass the `patient` object from the API response to `<app-json-viewer [json]="patientResource">` [Inference based on architecture.md#4-component-design, Component: JsonViewerComponent].

**Post Patient action:**

The "Post Patient" button calls `ApiService.postPatient(identifier)` which hits `POST /api/patients/{identifier}/post` with `session_id` as a query parameter [Source: architecture.md#6-api-specifications, ADR-004].

Expected success response:

```json
{
  "success": true,
  "data": {
    "fhir_id": "742",
    "server_response": { ... }
  },
  "message": "Patient posted successfully"
}
```

[Source: architecture.md#6-api-specifications]

The component must extract `data.fhir_id` and display it [Source: prd.md#FR-015 AC "assigned FHIR ID is displayed and stored"].

Expected error response (per ADR-005):

```json
{
  "success": false,
  "error": {
    "code": "FHIR_SERVER_UNREACHABLE",
    "message": "Could not connect to FHIR server at localhost:8080",
    "details": "Connection refused"
  }
}
```

[Source: architecture.md#ADR-005]

Error codes to handle: `PATIENT_NOT_FOUND`, `FHIR_SERVER_UNREACHABLE`, `FHIR_SERVER_ERROR` [Source: architecture.md#ADR-005].

**FHIR ID persistence:**

After a successful post, the backend stores the assigned FHIR ID in its session state [Source: architecture.md#5-data-model, SessionState]. Subsequent calls to `GET /api/patients/{identifier}` will return `fhir_id` with the stored value [Source: architecture.md#6-api-specifications]. The component should display this ID if present (e.g., "FHIR ID: 742" badge or label) [Inference — AC #7 requires "the FHIR ID is shown"].

**Placeholder state:**

When no patient is selected (on initial load or if selection is cleared), display "Select a patient to view details" instead of the JSON viewer and Post Patient button [Source: prd.md#FR-002 AC "Given no patient is selected, then the detail panel shows a placeholder message"].

**Session ID:**

ADR-004 mandates that all API requests requiring session context include `session_id` [Source: architecture.md#ADR-004]. The `postPatient()` call must include the session ID. The ApiService is responsible for injecting the session ID (via SessionService) [Source: architecture.md#4-component-design, Component: ApiService].

**Styling:**

Use Tailwind utility classes for layout and Angular Material components for buttons (e.g., `mat-raised-button` with primary color) [Source: architecture.md#ADR-006]. Display success messages in green, error messages in red (use Tailwind text-color utilities or Angular Material color theming) [Inference].

**File paths:**

Component files:
- `frontend/src/app/components/patient-detail/patient-detail.component.ts`
- `frontend/src/app/components/patient-detail/patient-detail.component.html`
- `frontend/src/app/components/patient-detail/patient-detail.component.css`
- `frontend/src/app/components/patient-detail/patient-detail.component.spec.ts`

Selector: `app-patient-detail` per ADR-006 [Source: architecture.md#ADR-006].

**Integration:**

This component is rendered in the dashboard shell created in story 3.2 (dashboard-layout), adjacent to or below the PatientListComponent [Source: prd.md#FR-013, architecture.md#4-component-design]. The parent container is responsible for wiring the patient selection event from PatientListComponent to this component [Inference — parent-child or service-based communication].

**Dependencies (blocked by):**

- Story 4.1 (patient-list) — provides patient selection event [Source: epics.md#Epic 4 dependencies]
- Story 3.3 (json-viewer) — provides JsonViewerComponent for syntax-highlighted JSON display [Source: epics.md#Epic 4 dependencies]

## Testing — LOCKED

<!-- LOCKED. External dev tools must not edit Testing. -->

**Strategy:**

Unit test the component in isolation with a mocked ApiService and JsonViewerComponent. Integration test the full workflow with backend and PatientListComponent.

**Unit tests (PatientDetailComponent.spec.ts):**

1. **Display patient JSON on selection (AC #1, #2):**
   - Mock ApiService.getPatient(identifier) to return `{success: true, data: {patient: {resourceType: "Patient", name: [...], ...}, fhir_id: null}}`
   - Trigger patient selection (set @Input or emit from service)
   - Verify component calls ApiService.getPatient(identifier)
   - Verify `patientResource` property is populated
   - Verify JsonViewerComponent receives the patient JSON as input
   - Verify required fields (name, address, birthDate, gender, telecom, identifier) are present in mock data (AC #2)

2. **Placeholder when no selection (AC #3):**
   - Initialize component without setting selected patient
   - Verify "Select a patient to view details" message is displayed
   - Verify JsonViewerComponent is not rendered
   - Verify Post Patient button is not rendered

3. **Post Patient button visible when patient selected (AC #4):**
   - Mock patient selection and getPatient response
   - Verify "Post Patient" button is rendered
   - Verify button is enabled

4. **Post Patient success (AC #5, #7):**
   - Mock patient selection
   - Mock ApiService.postPatient(identifier) to return `{success: true, data: {fhir_id: "742", server_response: {}}, message: "Patient posted successfully"}`
   - Click Post Patient button
   - Verify ApiService.postPatient(identifier) was called
   - Verify success message "Patient posted successfully" is displayed
   - Verify FHIR ID "742" is displayed in the panel
   - Verify component state updates to reflect FHIR ID

5. **Post Patient error handling (AC #6):**
   - Mock patient selection
   - Mock ApiService.postPatient(identifier) to return `{success: false, error: {code: "FHIR_SERVER_UNREACHABLE", message: "Could not connect", details: "..."}}`
   - Click Post Patient button
   - Verify error message "Could not connect" is displayed
   - Verify no FHIR ID is shown

6. **FHIR ID indicator when patient already posted (AC #7):**
   - Mock ApiService.getPatient(identifier) to return `{success: true, data: {patient: {...}, fhir_id: "742"}}`
   - Trigger patient selection
   - Verify FHIR ID "742" is displayed in the panel
   - Verify indicator shows patient has already been posted (e.g., badge or label)

**Integration tests (e2e or manual):**

1. **Full workflow (AC #1-#7):**
   - Start backend with patients.txt and FHIR server running
   - Load Angular app
   - Click a patient in PatientListComponent
   - Verify PatientDetailComponent displays FHIR JSON with syntax highlighting
   - Verify required FHIR fields are visible in JSON
   - Click "Post Patient" button
   - Verify success message and FHIR ID appear
   - Select the same patient again
   - Verify FHIR ID indicator shows the patient is already posted

2. **Error scenario: FHIR server unreachable (AC #6):**
   - Stop FHIR server
   - Select a patient
   - Click "Post Patient"
   - Verify error message "FHIR server unreachable" is displayed

3. **Placeholder state (AC #3):**
   - Load app without selecting a patient
   - Verify placeholder message is displayed in patient detail panel

**Edge cases:**

- Patient with minimal FHIR fields (only required fields populated)
- Patient with very large JSON payload (hundreds of lines) — verify JsonViewerComponent scrolls correctly
- Rapid selection changes (click different patients in quick succession) — verify component updates correctly without race conditions
- Clicking Post Patient twice rapidly — verify duplicate posts are prevented or handled gracefully
