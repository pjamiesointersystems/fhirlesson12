# 6.2: Build Results Panel with FHIR IDs and Error Display

**Story ID:** 6.2
**Epic:** 6 — Server Submission & Results UI
**Slug:** results-panel
**Status:** ready-for-dev

---

## Story

**As an** instructor
**I want** to see the Patient FHIR ID, all Observation IDs, server response JSON, and error details after posting
**So that** learners can observe the final output of the FHIR bundle lifecycle demo

---

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given the app is loaded, when the ResultsPanelComponent renders, then it displays a placeholder message indicating no results yet (e.g., "Post a bundle to see results here")
2. Given a bundle has been posted successfully, when the ResultsPanelComponent receives the server response, then it displays the Patient FHIR ID in a clearly labeled section
3. Given a bundle has been posted successfully, when the ResultsPanelComponent receives the server response, then it displays all Observation FHIR IDs in a scrollable list with a count label (e.g., "100 Observations Created")
4. Given a bundle has been posted successfully, when the instructor looks at the results panel, then the full server response JSON is displayed in a collapsible or scrollable section using the JsonViewerComponent
5. Given the bundle post operation failed (FHIR server unreachable, server error, no bundle built), when the ResultsPanelComponent receives the error, then it displays the error code and error message in a prominent alert/banner
6. Given error details are available, when the error is displayed, then the error details field (if present in the response envelope) is shown for debugging

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

**This story creates the ResultsPanelComponent**, the final piece of the FHIR demo lifecycle UI. It displays the outcome of posting a bundle to the FHIR server. [Inference]

### Architecture Context

The ResultsPanelComponent is part of the Server Submission & Results workflow stage. [Source: architecture.md#4-component-design — "ResultsPanelComponent: Display server response after posting, including assigned FHIR IDs (Patient ID, Observation IDs) and any errors"]

This component is **display-only** — it does not trigger any actions. It receives data from the BundlePanelComponent (story 6.1) after the bundle post operation completes. [Source: architecture.md#4-component-design — "Interfaces Required: Receives results from BundlePanelComponent"]

### Functional Requirements Coverage

**FR-009: Response Viewer with Assigned IDs — MUST** [Source: prd.md#FR-009]
- AC 1 requires: "Given a bundle has been posted successfully, then the Patient FHIR ID is displayed"
- AC 2 requires: "Given a bundle has been posted successfully, then all Observation FHIR IDs are listed"
- AC 3 requires: "Given IDs are displayed, then they are clearly labeled (Patient ID vs. Observation IDs)"

This story satisfies FR-009 fully via AC #2, #3 above.

**NFR-006: Error Visibility — MUST** [Source: prd.md#NFR-006]
- Requirement: "Every error scenario produces a visible message in the relevant dashboard panel"
- Measurement: "Test each error scenario (server down, missing file, bad input) and verify UI feedback"

This story satisfies the error display part of NFR-006 via AC #5, #6 above. [Source: prd.md#NFR-006]

### Data Model

The component receives data from the standardized response envelope defined in ADR-005. [Source: architecture.md#ADR-005]

**Success response structure** (from POST /api/bundles/post): [Source: architecture.md#6-api-specifications — POST /api/bundles/post]
```json
{
  "success": true,
  "data": {
    "patient_id": "742",
    "observation_ids": ["743", "744", "745", ...],
    "bundle_type": "transaction",
    "server_response": { "resourceType": "Bundle", "type": "transaction-response", ... }
  },
  "message": "Bundle posted successfully — 101 resources created"
}
```

**Error response structure**: [Source: architecture.md#ADR-005]
```json
{
  "success": false,
  "error": {
    "code": "FHIR_SERVER_UNREACHABLE",
    "message": "Could not connect to FHIR server at localhost:8080",
    "details": "Connection refused"
  }
}
```

The component must handle both shapes. Use a conditional in the template: `*ngIf="postResult?.success"` for success case, `*ngIf="postResult?.success === false"` for error case, `*ngIf="!postResult"` for placeholder. [Inference]

### UI/UX Guidance

The results panel is the **payoff moment** in the demo. The instructor shows learners:
1. The Patient FHIR ID assigned by the server
2. The list of Observation IDs (scrollable if many)
3. The full FHIR Bundle response JSON (for learners who want detail)

Use Material cards or sections to organize the display. Label each section clearly: "Patient FHIR ID", "Observation IDs", "Server Response". [Inference — matches Material design patterns]

The Observation IDs list may be long (100+ items). Use a scrollable container with a max height, or a Material list component with virtual scrolling if performance is a concern. For the MVP, a simple scrollable div is sufficient. [Inference]

The server response JSON is large. Display it using the shared `JsonViewerComponent` (created in story 3.3) inside a collapsible section (Material expansion panel or a toggled div). [Source: architecture.md#4-component-design — "JsonViewerComponent: Render any FHIR JSON with syntax highlighting"]

### Error Handling

All possible error codes from POST /api/bundles/post must be handled: [Source: architecture.md#6-api-specifications]
- `NO_BUNDLE` — bundle was not built before posting
- `FHIR_SERVER_UNREACHABLE` — FHIR server is down or network issue
- `FHIR_SERVER_ERROR` — FHIR server returned 4xx/5xx

Display the error code (e.g., "FHIR_SERVER_UNREACHABLE") and the human-readable message (e.g., "Could not connect to FHIR server at localhost:8080"). If the `error.details` field is present, show it in a collapsible section for debugging. [Source: architecture.md#ADR-005 — error envelope includes details field]

Use Angular Material `mat-card` with error styling, or `mat-alert` if available, to make errors prominent. Apply red or orange color to signal failure. [Inference — standard error UI pattern]

### Integration Points

**Input data**: The component receives the post result from BundlePanelComponent (story 6.1). Two integration patterns are possible: [Inference]

1. **@Input() binding**: Parent component (e.g., AppComponent or a shared dashboard component) passes the result as an `@Input()`:
   ```typescript
   @Input() postResult: any; // or define a PostResultModel
   ```
   BundlePanelComponent emits the result via `@Output()` event, parent catches it and passes to ResultsPanelComponent.

2. **Shared service/observable**: BundlePanelComponent publishes the result to a shared service (e.g., a ResultsService with a BehaviorSubject), and ResultsPanelComponent subscribes to it in `ngOnInit()`.

Either pattern is acceptable. The @Input() approach is simpler for a single-page dashboard. The service approach is more scalable if multiple components need the result. Choose based on the dashboard layout implemented in Epic 3. [Inference]

**JsonViewerComponent**: This shared component (created in story 3.3) takes JSON data as input and renders it with syntax highlighting. [Source: architecture.md#4-component-design — "JsonViewerComponent: Input: JSON object or string. Output: rendered highlighted JSON"]

Use it to display the `server_response` object:
```html
<app-json-viewer [json]="postResult.data.server_response"></app-json-viewer>
```

### State Management

The component tracks: [Inference]
- `postResult`: the raw response object from BundlePanelComponent
- `hasResult`: boolean flag — true if postResult is defined
- `isSuccess`: boolean flag — true if postResult.success === true
- `isError`: boolean flag — true if postResult.success === false

These flags drive template conditionals for placeholder / success / error views.

### Styling and Conventions

Follow ADR-006 naming conventions: [Source: architecture.md#ADR-006]
- Component file: `results-panel.component.ts`
- Template: `results-panel.component.html`
- Styles: `results-panel.component.css` (or .scss if configured)
- Use Tailwind utility classes for layout and spacing
- Use Angular Material components: `mat-card`, `mat-list`, `mat-expansion-panel` (optional for collapsible sections)

Use semantic HTML and ARIA labels for accessibility (e.g., label the Observation IDs list with an `<h3>` or `aria-label`). [Inference — good practice for dashboard UI]

### Non-Functional Requirements

**NFR-006: Error Visibility** — This component is the primary fulfillment of NFR-006 for the post operation. Every error from the backend must be displayed here. Test with: [Source: prd.md#NFR-006]
- FHIR server stopped — verify `FHIR_SERVER_UNREACHABLE` error displayed
- No bundle built — verify `NO_BUNDLE` error displayed
- FHIR server returns 500 — verify `FHIR_SERVER_ERROR` displayed

**NFR-003: Usability for Live Demo** — The results must be easy for the instructor to point at during the demo. Use large, clear labels and good spacing. The Patient ID and Observation count should be immediately visible without scrolling. [Source: prd.md#NFR-003]

### Demo Lifecycle Completion

This story completes the full FHIR Bundle lifecycle demo: [Inference — synthesizing PRD and architecture]
1. **Patient Management (Epic 4)**: Instructor selects a patient
2. **Observation Generation (Epic 5)**: Instructor generates observations
3. **Bundle Construction (Epic 5)**: Instructor builds a bundle
4. **Submission (Epic 6, story 6.1)**: Instructor posts the bundle
5. **Results Display (Epic 6, story 6.2)**: Instructor and learners see the Patient ID, Observation IDs, and server response

After this story, the app satisfies the core business goal: "Instructor completes the full FHIR Bundle lifecycle demo entirely within the browser UI." [Source: prd.md#Goals-and-Objectives — "UG-1: Instructor can demo the complete FHIR Bundle lifecycle without leaving the browser"]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

### Test Strategy

This component is **display-only** with no HTTP calls or complex logic. Testing focuses on:
- **Unit tests** for data parsing and template conditionals
- **Integration tests** for JsonViewerComponent integration
- **Manual tests** for UX verification with real data

### Unit Tests (ResultsPanelComponent)

**Test: "Displays placeholder when no result is present"**
- Arrange: Set `postResult = null` or `undefined`
- Act: Render component
- Assert: Placeholder text is visible, success/error sections are not visible

**Test: "Displays Patient ID and Observation IDs on success"**
- Arrange: Set `postResult` to a success envelope with `patient_id = "742"` and `observation_ids = ["743", "744"]`
- Act: Render component
- Assert: Patient ID "742" is displayed in labeled section, Observation IDs "743" and "744" are listed

**Test: "Displays observation count label"**
- Arrange: Set `postResult` with 100 observation IDs
- Act: Render component
- Assert: Label "100 Observations Created" (or similar) is visible

**Test: "Displays server response JSON in JsonViewerComponent"**
- Arrange: Set `postResult` with `server_response` object
- Act: Render component
- Assert: `<app-json-viewer>` is rendered with correct [json] input binding

**Test: "Displays error code and message on failure"**
- Arrange: Set `postResult` to error envelope with `code = "FHIR_SERVER_UNREACHABLE"` and `message = "Could not connect"`
- Act: Render component
- Assert: Error code and message are displayed, success section is not visible

**Test: "Displays error details when available"**
- Arrange: Set `postResult` to error envelope with `details = "Connection refused"`
- Act: Render component
- Assert: Error details "Connection refused" are displayed (possibly in a collapsible section)

**Test: "Hides error details when not present"**
- Arrange: Set `postResult` to error envelope with no `details` field
- Act: Render component
- Assert: No error details section is rendered

### Integration Tests

**Test: "JsonViewerComponent receives server response JSON"**
- Arrange: Create ResultsPanelComponent with success result including `server_response`
- Act: Render component
- Assert: JsonViewerComponent's `@Input() json` property receives the `server_response` object

**Test: "Component integrates with parent via @Input()"**
- Arrange: Create parent component that passes postResult as @Input
- Act: Update parent's postResult property
- Assert: ResultsPanelComponent re-renders with new data

### Edge Cases to Test

1. **Empty observation list**: `observation_ids = []` — verify count label shows "0 Observations Created"
2. **Large observation list**: 1000+ IDs — verify scrollable container works, no performance issues
3. **Missing fields in success response**: `patient_id` is null — verify component handles gracefully (display "N/A" or skip label)
4. **Error with no details field**: verify component does not crash, details section is hidden
5. **Rapid result updates**: Post multiple bundles in sequence — verify component clears previous result and displays new one

### Verification Approach

- Run Angular unit tests with `ng test` — all component tests pass
- Manual walkthrough:
  1. Load app, select patient, generate observations, build bundle, post bundle
  2. Verify ResultsPanelComponent displays Patient ID and list of Observation IDs
  3. Verify server response JSON is displayed with syntax highlighting
  4. Stop FHIR server, build and post bundle — verify error message displayed
  5. Verify error details (if present) are shown
- Visual inspection: verify labels are clear, spacing is good, scrollable areas work
- No test code is written in this story file — tests are implemented in the codebase. [Inference]
