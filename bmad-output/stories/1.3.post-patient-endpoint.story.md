# 1.3: Post Patient to FHIR Server

**Story ID:** 1.3
**Epic:** 1 — Backend API Foundation
**Slug:** post-patient-endpoint
**Status:** ready-for-dev

## Story

**As a** instructor
**I want** to post an individual Patient resource to the FHIR server via the API
**So that** I can demonstrate single-resource creation and obtain a FHIR server ID for subsequent Batch Bundle operations.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `POST /api/patients/{identifier}/post` posts the Patient resource to the FHIR server and returns the server-assigned FHIR ID in the success response envelope.
2. The endpoint accepts a `session_id` query parameter to support future session-based workflows.
3. The endpoint returns a 400 error with code `PATIENT_NOT_FOUND` if the identifier does not match any loaded patient.
4. The endpoint returns a 502 error with code `FHIR_SERVER_UNREACHABLE` if the FHIR server cannot be contacted.
5. The endpoint returns a 502 error with code `FHIR_SERVER_ERROR` if the FHIR server returns an error response.
6. After successful posting, the patient's FHIR server ID is stored in-memory and returned by `GET /api/patients/{identifier}`.
7. The endpoint uses FHIR server credentials from environment variables (never exposed to frontend).

### Architecture Pattern
[Source: architecture.md#6-api-specifications]
**`POST /api/patients/{identifier}/post`** specification:
- Purpose: Post the patient resource to the FHIR server
- Query params: `session_id` (UUID)
- Response:
```json
{
  "success": true,
  "data": {
    "fhir_id": "742",
    "server_response": { ... }
  },
  "message": "Patient posted successfully"
}
```
- Errors: 400 `PATIENT_NOT_FOUND`, 502 `FHIR_SERVER_UNREACHABLE`, 502 `FHIR_SERVER_ERROR`

### FHIR Server Integration
[Source: architecture.md#ADR-003]
**ADR-003: Backend-only FHIR server credentials** — FHIR server URL and credentials must NEVER appear in frontend code or API responses. Backend reads from environment variables (configured in story 1.1):
- `FHIR_SERVER_URL` (e.g., `http://127.0.0.1:8080/csp/healthshare/demo/fhir/r4`)
- `FHIR_SERVER_USER` (e.g., `_System`)
- `FHIR_SERVER_PASS` (e.g., `ISCDEMO`)

[Inference] To post a Patient resource to the FHIR server:
1. Serialize the Patient resource to JSON (use `patient_resource.json()` or `.dict()` depending on Pydantic v1 API)
2. POST to `{FHIR_SERVER_URL}/Patient` with:
   - Header: `Content-Type: application/fhir+json`
   - Header: `Authorization: Basic {base64(user:pass)}`
   - Body: serialized Patient JSON
3. Parse response to extract the `id` field from the returned Patient resource

[Source: sharding-context.md#Existing Python Code Being Wrapped]
The existing code likely uses `requests.post()` with Basic auth. The service layer should follow the same pattern.

### Error Handling
[Source: architecture.md#ADR-005]
All error responses must use the standardized envelope with `success: false` and `error` dict containing `code`, `message`, and `details`.

[Source: prd.md#NFR-006]
**NFR-006: Error Visibility** — all errors must be visible in the UI. This endpoint must return clear error responses for:
- Patient not found (input validation error)
- FHIR server unreachable (network/connection error)
- FHIR server error (server returned 4xx/5xx)

[Inference] Use Python exceptions in the service layer:
- Define custom exceptions: `PatientNotFoundError`, `FHIRServerUnreachableError`, `FHIRServerError`
- Catch `requests.exceptions.ConnectionError` → raise `FHIRServerUnreachableError`
- Catch `requests.exceptions.Timeout` → raise `FHIRServerUnreachableError`
- Check `response.status_code` → if not 2xx, raise `FHIRServerError` with details
- Router catches these exceptions and converts to appropriate HTTP responses with error codes

### Session ID Parameter
[Source: architecture.md#ADR-004]
**ADR-004: Server-side session state with session ID** — every API request should include `session_id` as a query parameter or header. The frontend sends a UUID with each request; the backend uses it to look up session-specific data.

[Inference] For this endpoint, the `session_id` parameter is included for consistency (AC #2), but the endpoint does not currently use it for state lookup. Future stories may use session state to track which patient was last posted. For now, treat it as optional and log it if provided.

### FHIR ID Storage
[Source: architecture.md#5-data-model]
The `PatientService` maintains a dict `{identifier: fhir_id}` in-memory (ADR-002: no database). After successfully posting a patient, store the server-assigned ID in this dict so that:
1. `GET /api/patients/{identifier}` returns the FHIR ID in the response
2. Subsequent bundle construction can determine whether to use Batch (FHIR ID known) or Transaction (FHIR ID unknown)

[Inference] The FHIR server response to a successful POST is a Patient resource with an `id` field. Extract `response_json["id"]` and store it.

### Response Structure
[Source: architecture.md#6-api-specifications]
Success response includes:
- `fhir_id` (string) — server-assigned ID, e.g., "742"
- `server_response` (dict) — full FHIR server response for debugging/transparency

[Inference] The `server_response` is useful for the instructor to see what the FHIR server returned (e.g., full Patient resource with assigned ID, location header, etc.). Include `response.json()` in the data envelope.

### Testing Notes
This endpoint requires a running FHIR server for integration testing. For error scenarios:
- **Patient not found:** Use an invalid identifier (e.g., "999-999-9999")
- **FHIR server unreachable:** Stop the FHIR server before calling the endpoint
- **FHIR server error:** Requires invalid patient data or server misconfiguration (may be difficult to simulate — consider mocking the FHIR server response in unit tests)

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

**Strategy:** Unit tests for service logic (with mocked `requests`), integration tests for end-to-end behavior (require running FHIR server).

**What to verify:**
1. `PatientService.post_patient(identifier)` successfully posts to FHIR server and returns FHIR ID (AC #1)
2. Service stores FHIR ID in-memory after successful post (AC #6)
3. Service raises `PatientNotFoundError` for invalid identifier (AC #3)
4. Service raises `FHIRServerUnreachableError` for connection errors (AC #4)
5. Service raises `FHIRServerError` for HTTP error responses (AC #5)
6. Endpoint returns 200 success response with FHIR ID for valid patient (AC #1)
7. Endpoint accepts `session_id` query parameter without error (AC #2)
8. Endpoint returns 400 `PATIENT_NOT_FOUND` for invalid identifier (AC #3)
9. Endpoint returns 502 `FHIR_SERVER_UNREACHABLE` when server is down (AC #4)
10. Endpoint returns 502 `FHIR_SERVER_ERROR` when server returns error (AC #5)
11. `GET /api/patients/{identifier}` returns stored FHIR ID after posting (AC #6)

**Test types:**
- **Unit:** Test `PatientService.post_patient()` with mocked `requests.post()` for all scenarios (success, connection error, HTTP error)
- **Integration:** Call `POST /api/patients/{identifier}/post` via FastAPI TestClient with a running FHIR server
- **Integration (error scenarios):** Test with FHIR server stopped, test with invalid identifier

**Scenarios:**
- **Happy path:** POST patient "356-444-9972" → FHIR server returns 201 with assigned ID → endpoint returns success with FHIR ID → GET patient returns updated fhir_id
- **Patient not found:** POST patient "999-999-9999" → endpoint returns 400 with `PATIENT_NOT_FOUND`
- **FHIR server down:** Stop FHIR server → POST patient → endpoint returns 502 with `FHIR_SERVER_UNREACHABLE`
- **FHIR server error:** (simulate) FHIR server returns 500 → endpoint returns 502 with `FHIR_SERVER_ERROR`
- **Session ID parameter:** POST with `?session_id=<uuid>` → endpoint accepts and processes normally

**Edge cases:**
- Double-post: POST same patient twice → second post succeeds (FHIR server allows update or returns 200), FHIR ID is updated
- Malformed FHIR server response: server returns 200 but response JSON is missing `id` field → service should handle gracefully (raise error or log warning)
- Empty/null identifier in URL path → FastAPI routing returns 404 (not this endpoint's concern)

**Fixtures:**
- Use the existing `patients.txt` file (5 patients)
- FHIR server running at localhost:8080 with credentials `_System:ISCDEMO`
- Mock `requests.post()` for unit tests to avoid dependency on running server

**Mocking strategy for unit tests:**
- Mock `requests.post()` to return:
  - Success: `response.status_code = 201`, `response.json() = {"resourceType": "Patient", "id": "742", ...}`
  - Connection error: raise `requests.exceptions.ConnectionError`
  - HTTP error: `response.status_code = 500`, `response.json() = {"error": "..."}`

**No coverage target specified.** Focus on proving all 7 acceptance criteria. Aim for high coverage of the `post_patient()` method and error paths.
