# 5.2: Bundle Panel Component

**Story ID:** 5.2
**Epic:** 5 — Observation & Bundle UI
**Slug:** bundle-panel
**Status:** ready-for-dev

---

## Story

**As an** instructor
**I want** to build a FHIR Bundle (Batch or Transaction) from generated observations with one click, see which type was auto-selected and why, and preview the full bundle JSON
**So that** I can demonstrate the difference between Batch and Transaction bundles to learners and show them the complete bundle structure before posting

---

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given observations have been generated for a selected patient, when I click "Build Bundle," then the backend constructs the appropriate bundle type (Transaction if no FHIR ID, Batch if FHIR ID exists) and returns the bundle JSON
2. Given a bundle has been built, then the bundle type ("Batch" or "Transaction") is clearly indicated in the bundle panel with a visual badge or label
3. Given a bundle has been built, then an explanation of why that type was selected is displayed (e.g., "Transaction — Patient has no FHIR server ID, using urn:uuid references" or "Batch — Patient ID 742 exists on server")
4. Given a bundle has been built, then the full bundle JSON is displayed in the bundle panel using JsonViewerComponent, including all entries and entry count
5. Given the build bundle request fails (no observations generated, patient not selected, server error), then a clear error message is displayed in the bundle panel
6. Given no observations have been generated yet, when the bundle panel renders, then the "Build Bundle" button is disabled or shows a message indicating observations must be generated first

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

### Component Responsibility

BundlePanelComponent provides the UI for building a FHIR Bundle from generated observations and previewing the bundle JSON before posting. It displays the auto-selected bundle type (Batch vs Transaction) with an explanation. This is the "core teaching moment" where learners understand the Bundle logic. [Source: architecture.md#4-component-design, BundlePanelComponent section; prd.md EPIC-003 description]

### Functional Requirements Coverage

**FR-005: Transaction Bundle Construction** — When the patient has no known FHIR server ID, the backend builds a Transaction Bundle with urn:uuid references. The bundle type indicator shows "Transaction" with the reason "Patient has no FHIR server ID — using urn:uuid references". [Source: prd.md#FR-005]

**FR-006: Batch Bundle Construction** — When the patient has a known FHIR server ID (from a prior POST), the backend builds a Batch Bundle with observations referencing the patient's FHIR ID. The bundle type indicator shows "Batch" with the reason including the patient's FHIR ID. [Source: prd.md#FR-006]

**FR-007: Bundle Type Auto-Selection** — The backend automatically selects the bundle type based on whether the patient has a FHIR ID. The component displays the selection and reason. The backend logic for selection is in BundleService (from Epic 2). [Source: prd.md#FR-007]

The full bundle JSON displayed includes all Patient and Observation entries, with each entry showing its request method (POST) and resource URL. [Source: prd.md#FR-005, FR-006 acceptance criteria]

### Architecture Constraints

**ADR-001 (REST API):** Component calls `ApiService.buildBundle(identifier)` which invokes POST /api/bundles/build. All responses are JSON. [Source: architecture.md#ADR-001]

**ADR-004 (Session State):** The backend uses session_id to retrieve previously generated observations and the patient's FHIR ID (if it exists). The component passes the patient identifier; the backend looks up session state server-side. The component does NOT hold bundle state long-term — it displays the returned bundle JSON. [Source: architecture.md#ADR-004]

**ADR-005 (Error Envelope):** Component checks `success` field in API response. On `success: false`, extract `error.message` and display in the panel. Expected error codes: `PATIENT_NOT_FOUND`, `NO_OBSERVATIONS`, `INTERNAL_ERROR`. [Source: architecture.md#ADR-005]

**ADR-006 (Naming & Styling):** Component file: `bundle-panel.component.ts`, selector: `app-bundle-panel`. Use Angular Material components (mat-card, mat-raised-button, mat-chip for badge) and Tailwind utility classes for layout. TypeScript model file: `models/bundle.model.ts`. [Source: architecture.md#ADR-006]

### Data Flow

1. User has already generated observations via ObservationPanelComponent (5.1) — backend holds observations in session state
2. User clicks "Build Bundle" → component calls `ApiService.buildBundle(selectedPatientIdentifier)` → backend builds appropriate bundle type and returns JSON
3. Component receives response:
   - `bundle_type`: "transaction" or "batch"
   - `bundle_type_reason`: human-readable explanation
   - `entry_count`: total entries in bundle (1 Patient + N Observations for Transaction, or N Observations for Batch)
   - `bundle_json`: full FHIR Bundle resource
4. Component displays bundle type badge, reason text, entry count, and passes `bundle_json` to JsonViewerComponent

[Inference: The component should listen to or receive input indicating whether observations have been generated (e.g., an @Input observationCount or shared service state) to enable/disable the "Build Bundle" button. Coordinate with ObservationPanelComponent (5.1) implementation for state sharing.]

### API Integration

**POST /api/bundles/build**
Request body: `{ session_id, identifier }`
Success response:
```json
{
  "success": true,
  "data": {
    "bundle_type": "transaction",
    "bundle_type_reason": "Patient has no FHIR server ID — using Transaction Bundle with urn:uuid references",
    "entry_count": 101,
    "bundle_json": {
      "resourceType": "Bundle",
      "type": "transaction",
      "entry": [
        {
          "fullUrl": "urn:uuid:...",
          "resource": { "resourceType": "Patient", ... },
          "request": { "method": "POST", "url": "Patient" }
        },
        {
          "fullUrl": "urn:uuid:...",
          "resource": { "resourceType": "Observation", ... },
          "request": { "method": "POST", "url": "Observation" }
        },
        ...
      ]
    }
  }
}
```
Error response: `{ success: false, error: { code: "NO_OBSERVATIONS", message: "...", details: "..." } }`
[Source: architecture.md#6-api-specifications, POST /api/bundles/build]

### UI/UX Notes

- Bundle panel should be disabled or show placeholder text when no observations have been generated (AC #6). This depends on ObservationPanelComponent state. Consider a shared service or @Input from parent to communicate observation count > 0. [Inference based on workflow dependency]
- Bundle type badge styling: suggest using mat-chip with color coding — e.g., "Transaction" in blue/purple (primary), "Batch" in green/teal (accent). This provides immediate visual distinction for learners. [Inference based on Material Design best practices]
- Bundle type reason should be displayed as a secondary text block (e.g., mat-card-subtitle or a <p> with muted styling) below the badge. [Inference based on UX hierarchy]
- Entry count can be displayed near the bundle type or as part of the JSON viewer header (e.g., "Bundle JSON (101 entries)"). [Inference]
- Full bundle JSON can be large (100+ observations). Ensure JsonViewerComponent has scrolling enabled. Confirm from 3.3 implementation. [Source: architecture.md#4-component-design, JsonViewerComponent]

### TypeScript Model

Create `frontend/src/app/models/bundle.model.ts`:
```typescript
export interface BundleResponse {
  bundle_type: 'batch' | 'transaction';
  bundle_type_reason: string;
  entry_count: number;
  bundle_json: any; // FHIR Bundle resource (could type as fhir.Bundle if fhir.resources types are available in frontend)
}
```
This interface matches the API response `data` object structure. [Source: architecture.md#6-api-specifications]
