# 2.1: Observation Generation Endpoints

**Story ID:** 2.1
**Epic:** 2 — Backend Observation & Bundle Endpoints
**Slug:** observation-endpoints
**Status:** ready-for-dev

## Story

**As a** frontend developer
**I want** REST endpoints to generate heart rate observations from file or synthetically
**so that** the observation panel can trigger generation and display results without handling FHIR logic directly

## Acceptance Criteria — LOCKED

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given the API is running and a valid patient identifier is sent to POST /api/observations/from-file, when the endpoint is called with a session_id and identifier in the request body, then observations are generated from the patient's data file and a success response is returned with the count of observations and sample JSON for the first two observations [Source: prd.md#FR-011]

2. Given the data file for a patient does not exist, when POST /api/observations/from-file is called, then a 400 response is returned with error code FILE_NOT_FOUND and a descriptive message [Source: architecture.md#ADR-005]

3. Given the API is running and a valid patient identifier and count (1-1000) are sent to POST /api/observations/synthetic, when the endpoint is called with session_id, identifier, and count in the request body, then synthetic observations are generated with random heart rate values and timestamps, and a success response is returned with the count and sample JSON [Source: prd.md#FR-011]

4. Given a count > 1000 is sent to POST /api/observations/synthetic, when the endpoint is called, then the count is capped at 1000 and 1000 observations are generated [Source: prd.md#FR-004]

5. Given a count < 1 is sent to POST /api/observations/synthetic, when the endpoint is called, then the count is defaulted to 1 and 1 observation is generated [Source: prd.md#FR-004]

6. Given observations are generated for a patient, when the observations are stored in session state, then they are keyed by session_id and patient identifier so subsequent bundle-build calls can retrieve them [Source: architecture.md#ADR-004]

7. Given a patient identifier that does not exist in the loaded patients, when either observation endpoint is called, then a 400 response is returned with error code PATIENT_NOT_FOUND [Source: architecture.md#ADR-005]

### Architecture Pattern

This story implements two REST endpoints in the FastAPI backend following the pattern established in Epic 1 (Story 1.1 and 1.2). The endpoints expose the observation generation logic from the existing Python codebase as API operations. [Source: architecture.md#ADR-001]

The service layer wraps existing classes:
- `HeartRateObservation` from observation.py [Source: architecture.md#component-design]
- `HeartRateFileBundleGenerator` from heartratefilebundlegenerator.py (for file-based generation)
- `heartratedatagenerator.py` logic (for synthetic generation)

### Data Model

Observations are stored in session state keyed by `session_id` and `patient identifier`. The session state schema (from state.py, established in Story 1.1) includes:
```python
observations: dict[str, dict[str, list[HeartRateObservation]]]
# Outer key: session_id (UUID)
# Inner key: patient identifier (e.g., "356-444-9972")
# Value: list of HeartRateObservation instances
```
[Source: architecture.md#ADR-004, architecture.md#5-data-model]

### Functional Requirements

**FR-011:** Backend API for observation generation [Source: prd.md#FR-011]
- POST /api/observations/from-file accepts session_id and identifier, reads the patient's heart rate data file (format: {identifier_no_dashes}.txt, e.g., 3564449972.txt), generates observations, stores them in session state, and returns count + sample JSON
- POST /api/observations/synthetic accepts session_id, identifier, and count (1-1000), generates synthetic observations with random heart rate values and timestamps, stores them in session state, and returns count + sample JSON
- If the data file does not exist, return FILE_NOT_FOUND error (400)
- If the patient identifier is unknown, return PATIENT_NOT_FOUND error (400)

**FR-004:** Synthetic observation generation [Source: prd.md#FR-004]
- Count must be capped at 1000 (if input > 1000, cap to 1000)
- Count must be floored at 1 (if input < 1, default to 1)

### API Contract

**POST /api/observations/from-file**
Request body:
```json
{
  "session_id": "uuid-string",
  "identifier": "356-444-9972"
}
```

Success response (200):
```json
{
  "success": true,
  "data": {
    "count": 100,
    "sample_observations": [
      { "resourceType": "Observation", "id": "...", "code": {...}, "valueQuantity": {...}, "effectiveDateTime": "..." },
      { "resourceType": "Observation", ... }
    ]
  },
  "message": "Generated 100 observations from file"
}
```

Error response (400 FILE_NOT_FOUND):
```json
{
  "success": false,
  "error": {
    "code": "FILE_NOT_FOUND",
    "message": "Data file not found for patient 356-444-9972",
    "details": "Expected file: 3564449972.txt"
  }
}
```

Error response (400 PATIENT_NOT_FOUND):
```json
{
  "success": false,
  "error": {
    "code": "PATIENT_NOT_FOUND",
    "message": "Patient with identifier 356-444-9972 not found",
    "details": ""
  }
}
```
[Source: architecture.md#ADR-005, architecture.md#6-api-specifications]

**POST /api/observations/synthetic**
Request body:
```json
{
  "session_id": "uuid-string",
  "identifier": "356-444-9972",
  "count": 50
}
```

Success response (200):
```json
{
  "success": true,
  "data": {
    "count": 50,
    "sample_observations": [
      { "resourceType": "Observation", ... },
      { "resourceType": "Observation", ... }
    ]
  },
  "message": "Generated 50 synthetic observations"
}
```

Error response (400 INVALID_INPUT):
```json
{
  "success": false,
  "error": {
    "code": "INVALID_INPUT",
    "message": "Invalid count parameter",
    "details": "Count must be between 1 and 1000"
  }
}
```
[Source: architecture.md#ADR-005, architecture.md#6-api-specifications]

### Integration Points

- **Existing Python classes:** The service layer must instantiate and call existing classes (HeartRateObservation, HeartRateFileBundleGenerator, heartratedatagenerator logic). These classes currently use `print()` for output — the service layer must capture return values instead. [Inference: refactor may be required to replace prints with returns]

- **Session state:** Observations must be stored in the session state object (state.py) so that Story 2.2 (bundle-build endpoint) can retrieve them. The session state is keyed by session_id (UUID), and within each session, observations are keyed by patient identifier. [Source: architecture.md#ADR-004]

- **Patient service dependency:** The observation service must validate that the patient identifier exists by querying the patient service (services/patient_service.py, created in Story 1.2). If the identifier is not found, return PATIENT_NOT_FOUND. [Source: architecture.md#4-component-design]

- **Data file location:** Heart rate data files are named {identifier_no_dashes}.txt (e.g., 3564449972.txt for patient 356-444-9972). The files are expected to be in the same directory as the backend code or a configurable data directory. [Inference: existing code stores files in repo root or a data/ folder]

### Environment and Configuration

- **FHIR server credentials:** Not needed for this story — observations are generated locally and stored in session state, not posted to the FHIR server. [Source: architecture.md#ADR-003]

- **File paths:** The existing heartratefilebundlegenerator.py logic reads files from a specific path. Ensure the path is configurable or defaults to a known location (e.g., `./{identifier_no_dashes}.txt` or `data/{identifier_no_dashes}.txt`). [Inference: check existing code for hardcoded paths]

### Naming Conventions

- **Backend:** snake_case for all Python variables, functions, file names. PascalCase for class names. [Source: architecture.md#ADR-006]
- **Router file:** routers/observations.py
- **Service file:** services/observation_service.py
- **Request models:** models/requests.py (ObservationFromFileRequest, ObservationSyntheticRequest)
- **Response model:** models/responses.py (ObservationResponse, extend ApiResponse if needed)
- **Endpoint paths:** /api/observations/from-file, /api/observations/synthetic (lowercase, kebab-case)
- **JSON keys:** snake_case (session_id, identifier, count, sample_observations)

### Error Handling

All errors must be returned in the standardized response envelope [Source: architecture.md#ADR-005]:
- FILE_NOT_FOUND (400): Data file does not exist for the patient
- PATIENT_NOT_FOUND (400): Patient identifier not found in loaded patients
- INVALID_INPUT (400): Count parameter out of range (handled by capping/floor, but include for edge cases)
- INTERNAL_ERROR (500): Unexpected exceptions during generation

### Notes for Implementation

- **Pydantic v1:** The backend uses Pydantic v1 (pinned by fhir.resources 6.1.0). Use `.dict()` and `.json()` methods, not v2 syntax. [Source: architecture.md#trade-off-pydantic-v1-compatibility]

- **Sample observations:** Return the first two observations as sample JSON for display in the frontend. Convert HeartRateObservation instances to dict using Pydantic's `.dict()` method.

- **Count validation:** Apply the count capping (1000 max) and floor (1 min) logic in the service layer before generating observations. Do not return an error if the count is out of range — just cap/floor and proceed. [Source: prd.md#FR-004]

- **Session state initialization:** If the session_id does not exist in session state, initialize it before storing observations. If observations already exist for the patient in this session, overwrite them (each generation replaces previous observations). [Inference: generation is idempotent within a session]

### Testing Strategy

**Unit tests** for services/observation_service.py:
- Test generate_from_file() with a valid patient identifier and existing data file — verify count and sample observations returned
- Test generate_from_file() with a patient identifier that has no data file — verify FILE_NOT_FOUND error raised
- Test generate_from_file() with an unknown patient identifier — verify PATIENT_NOT_FOUND error raised
- Test generate_synthetic() with valid identifier and count=50 — verify 50 observations generated and stored
- Test generate_synthetic() with count=1500 — verify count is capped to 1000
- Test generate_synthetic() with count=0 — verify count is floored to 1
- Test generate_synthetic() with count=-10 — verify count is floored to 1
- Test that observations are stored in session state keyed by session_id and identifier

**Integration tests** for routers/observations.py:
- Test POST /api/observations/from-file with valid session_id and identifier — verify 200 response with correct data structure (success=true, count, sample_observations)
- Test POST /api/observations/from-file with missing data file — verify 400 response with FILE_NOT_FOUND error code
- Test POST /api/observations/from-file with unknown patient identifier — verify 400 response with PATIENT_NOT_FOUND error code
- Test POST /api/observations/synthetic with valid inputs — verify 200 response with correct count and sample observations
- Test POST /api/observations/synthetic with count=1500 — verify response shows count=1000 (capped)
- Test POST /api/observations/synthetic with count=0 — verify response shows count=1 (floored)
- Test POST /api/observations/synthetic with unknown patient identifier — verify 400 response with PATIENT_NOT_FOUND error code

**Edge cases:**
- Empty or malformed request body — verify 422 Unprocessable Entity (FastAPI default validation)
- Missing session_id in request — verify validation error
- Data file exists but is empty or malformed — verify graceful error handling (FILE_NOT_FOUND or INVALID_INPUT)
- Concurrent requests with different session_ids — verify observations are isolated by session

**Fixtures and mocks:**
- Mock session state (state.py) for unit tests
- Mock patient service (services/patient_service.py) for unit tests to simulate patient lookups
- Use a test data directory with known heart rate data files for integration tests
- Mock or stub existing observation.py classes if needed to isolate service layer logic

**Coverage targets:**
- All AC (#1-#7) must have at least one test case proving the criterion
- All error codes (FILE_NOT_FOUND, PATIENT_NOT_FOUND, INVALID_INPUT) must be triggered and verified
- Happy path (valid inputs, successful generation) must be covered for both endpoints
