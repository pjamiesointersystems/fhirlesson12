# 1.2: Patient List and Detail Endpoints

**Story ID:** 1.2
**Epic:** 1 — Backend API Foundation
**Slug:** patient-endpoints
**Status:** ready-for-dev

## Story

**As a** frontend developer
**I want** REST endpoints to list all patients and retrieve individual patient details
**So that** the Angular dashboard can display the patient list and patient detail panels.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `GET /api/patients` returns a list of all patients with name and identifier fields in the success response envelope.
2. `GET /api/patients/{identifier}` returns the full FHIR Patient JSON resource and the patient's FHIR server ID (if known) in the success response envelope.
3. `GET /api/patients/{identifier}` returns a 400 error with code `PATIENT_NOT_FOUND` if the identifier does not match any loaded patient.
4. Patient data is loaded from `patients.txt` at backend startup and stored in memory.
5. The patient service wraps the existing `Patients` class from `patients.py` and stores FHIR server IDs for patients after they are posted.
6. Both endpoints respond within 2 seconds (p95) under normal conditions.

### Functional Requirements
[Source: prd.md#FR-010]
**FR-010: Backend API for Patient Operations** — the backend must expose REST endpoints to list patients, get patient details, and post patients to the FHIR server. This story covers the first two operations (list + detail). The POST operation is deferred to story 1.3.

Acceptance criteria from FR-010:
- `GET /api/patients` returns all patients as JSON
- `GET /api/patients/{identifier}` returns patient detail as FHIR JSON

[Source: prd.md#FR-001, FR-002]
**FR-001: Patient List Display** — the system displays all 5 patients from `patients.txt` with name and identifier.
**FR-002: Patient Detail View** — the system displays the full FHIR Patient JSON resource when a patient is selected.

### Architecture Pattern
[Source: architecture.md#4-component-design]
**PatientService** component wraps the existing `Patients` class from `patients.py`. It loads patients from files, provides patient lookup, and manages FHIR ID storage. This service is the bridge between the existing CLI-oriented code and the REST API layer.

[Source: architecture.md#6-api-specifications]
The API specifications for these endpoints:

**`GET /api/patients`**
- Response:
```json
{
  "success": true,
  "data": {
    "patients": [
      {"name": "Mary Johnson", "identifier": "356-444-9972"},
      ...
    ]
  }
}
```

**`GET /api/patients/{identifier}`**
- Response:
```json
{
  "success": true,
  "data": {
    "patient": { "resourceType": "Patient", ... },
    "fhir_id": "123" | null
  }
}
```
- Errors: 400 `PATIENT_NOT_FOUND`

### Data Model
[Source: architecture.md#5-data-model]
**Patient entity** (from file):
- `identifier` (string, key) — e.g., "356-444-9972"
- `resource` (fhir.resources.Patient) — the full FHIR Patient object
- `fhir_id` (string, optional) — server-assigned ID after posting, initially None
- `name` (string) — display name extracted from resource

The `PatientService` maintains:
1. A dict/list of loaded Patient resources keyed by identifier
2. A separate dict for FHIR server IDs (identifier → fhir_id)

### Wrapping Existing Code
[Source: sharding-context.md#Existing Python Code Being Wrapped]
The existing `patients.py` contains a `Patients` class that loads from `patients.txt` and stores Patient resources keyed by identifier. The file format is one identifier per line (e.g., "356-444-9972").

[Inference] The existing `Patients` class likely uses `print()` for output. The service layer must:
1. Instantiate the `Patients` class at startup
2. Call its load method to populate patient data
3. Provide clean `list_patients()` and `get_patient(identifier)` methods that return data structures (not print)

[Source: prd.md#Risks and Mitigations]
Risk: "Existing code uses print() for output, not return values." Mitigation: "Create service layer wrapping existing classes, replacing prints with returns."

### Naming Conventions
[Source: architecture.md#ADR-006]
- Service file: `services/patient_service.py` (snake_case)
- Service class: `PatientService` (PascalCase)
- Router file: `routers/patients.py` (snake_case)
- Functions/methods: snake_case (e.g., `list_patients`, `get_patient`)
- JSON response keys: snake_case (e.g., `fhir_id`, not `fhirId`)

### Response Envelope
[Source: architecture.md#ADR-005]
All responses must use the standardized envelope from story 1.1:
- Success: `{"success": true, "data": {...}, "message": "..."}`
- Error: `{"success": false, "error": {"code": "...", "message": "...", "details": "..."}}`

Error code for patient not found: `PATIENT_NOT_FOUND`

### Performance
[Source: prd.md#NFR-001]
**NFR-001: API Response Time** — p95 response time < 2 seconds for all endpoints except bundle posting. Patient list and detail are in-memory lookups — should respond in milliseconds. Verify with manual timing or FastAPI request logging during development.

### File Location
[Source: sharding-context.md#Existing Python Code Being Wrapped]
The `patients.txt` file is in the project root (alongside the existing CLI scripts). The `PatientService` should construct the correct relative or absolute path to load this file.

[Inference] The existing `patients.py` likely expects to run from the project root directory. When wrapping it, ensure the file path resolves correctly. Consider using `os.path.join(os.path.dirname(__file__), "..", "patients.txt")` or a config constant.

### FHIR ID Storage
[Source: architecture.md#5-data-model, architecture.md#ADR-002]
FHIR server IDs are stored in-memory (ADR-002: no database). The `PatientService` maintains a dict `{identifier: fhir_id}` that is initially empty. Story 1.3 will implement the POST endpoint that populates this dict after successfully posting a patient to the FHIR server.

For this story, `fhir_id` in the response will always be `null` until story 1.3 is completed.

### Integration with Story 1.1
[Source: story 1.1]
This story depends on the FastAPI scaffold from story 1.1:
- Response envelope models (`models/responses.py`)
- FastAPI app and CORS configuration (`main.py`)
- Router mounting pattern

The patients router will be mounted in `main.py` using FastAPI's `app.include_router()`.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

**Strategy:** Unit tests for service logic, integration tests for endpoint behavior.

**What to verify:**
1. `PatientService` correctly loads patients from `patients.txt` (AC #4)
2. `PatientService.list_patients()` returns all patients with name and identifier (AC #1)
3. `PatientService.get_patient(identifier)` returns full Patient resource for valid identifier (AC #2)
4. `PatientService.get_patient(identifier)` raises exception or returns None for invalid identifier (AC #3)
5. `GET /api/patients` endpoint returns success envelope with patient list (AC #1)
6. `GET /api/patients/{identifier}` endpoint returns success envelope with patient resource (AC #2)
7. `GET /api/patients/{identifier}` endpoint returns 400 error for invalid identifier (AC #3)
8. Response time < 2s (AC #6)

**Test types:**
- **Unit:** Test `PatientService` methods in isolation (mock file I/O if needed)
- **Integration:** Call endpoints via FastAPI TestClient, verify response structure and status codes

**Scenarios:**
- **Happy path (list):** Call `GET /api/patients` → receive 200 with 5 patients
- **Happy path (detail):** Call `GET /api/patients/356-444-9972` → receive 200 with Mary Johnson's FHIR Patient JSON
- **Patient not found:** Call `GET /api/patients/999-999-9999` → receive 400 with `PATIENT_NOT_FOUND` error code
- **Empty/null identifier:** Call `GET /api/patients/` (no identifier) → 404 (FastAPI default) or 400
- **Response structure:** Verify `success`, `data`, `message` fields present in success responses
- **FHIR resource structure:** Verify returned patient includes `resourceType: "Patient"`, `name`, `identifier`, etc.

**Edge cases:**
- Missing `patients.txt` file → service initialization fails (acceptable — should raise error at startup)
- Malformed line in `patients.txt` → log warning and skip, or fail fast (decision: fail fast to catch config issues early)
- Identifier with special characters (e.g., "356-444-9972" has dashes) → verify URL encoding works correctly

**Fixtures:**
- Use the existing `patients.txt` file in the repository (5 patients)
- No mocks needed for the file — it's a committed fixture

**No coverage target specified.** Focus on proving each AC. Aim for coverage of all three endpoints (list, detail, not-found).
